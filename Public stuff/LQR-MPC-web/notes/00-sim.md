## What this file is for

`code/sim.py` is the entire control theory of this course in one file with no
dependency on BLE, motors, or a sensor. `code/robot.py` implements the same
two functions — `read()` and `drive()` — against real hardware; everything
between those functions and the motors is pure math, and that math lives here.

Two consequences worth knowing up front:

- **Every number in [01-lqr.md](01-lqr.md), [02-mpc.md](02-mpc.md), and
  [03-lqr-vs-mpc.md](03-lqr-vs-mpc.md) is generated by `main()` at the bottom
  of this file.** If a number in the docs and a number `sim.py` prints ever
  disagree, the docs are wrong and should be regenerated, not the other way
  around.
- **A controller written against `sim.py` runs unchanged on the robot.**
  `run_lqr.py` and `run_mpc.py` import `lqr_gains_discrete` and
  `mpc_choose_speed` straight from here — swapping `robot.LineFollower` in for
  the plant model is the only thing that changes.

## The model

The state is two numbers: lateral offset $e$ [mm] and heading error $\theta$
[rad]. The dynamics are the standard small-angle lateral-tracking model for a
vehicle following a line at (possibly time-varying) forward speed $v$:

$$\dot e = v \sin\theta \approx v\theta \qquad
  \dot\theta = \omega - \kappa v$$

with $\omega$ [rad/s] the commanded yaw rate and $\kappa$ [1/mm] the curvature
of the line the robot is trying to follow. `step()` implements exactly this,
forward-Euler, one control period at a time:

```python
def step(e, theta, v, omega, kappa, dt=DT):
    e_next = e + dt * v * np.sin(theta)
    th_next = theta + dt * (omega - kappa * v)
    return e_next, th_next
```

Everything else in the file is either fitting a controller to this model
(the LQR half), or deciding what $v$ should be at each instant (the MPC half).

## Build constants

```python
V_REF = 150.0        # mm/s   nominal forward speed
TRACK_W = 96.0       # mm     distance between the two wheel contact patches
WHEEL_MAX = 400.0    # mm/s   wheel speed at motor_speed = 100%
E_MAX = 6.0          # mm     half-width of the sensor's usable linear region
DT = 0.05            # s      control period (20 Hz, = notification delay)

Q_E = 1.0            # cost per mm^2 of lateral error
Q_TH = 0.0           # cost per rad^2 of heading error
R_W = 25.0           # cost per (rad/s)^2 of yaw rate
```

These are the reference build's numbers — the same ones `code/calibrate.py`
measures on your own robot and writes to `code/calibration.json`. Only the
*ratios* $Q_E/R$ and $Q_\theta/R$ matter for the gains; see
[01-lqr.md](01-lqr.md#step-3-the-cost) for why.

## The LQR half

**`lqr_gains_analytic(v, q_e, q_th, r)`** is the closed-form continuous-time
solution derived by hand in
[01-lqr.md](01-lqr.md#solving-it-by-hand):

$$k_e = \sqrt{q_e/r}, \qquad k_\theta = \sqrt{q_\theta/r + 2vk_e}$$

**`dlqr(A, B, Q, R)`** is the general-purpose tool underneath everything else:
discrete-time infinite-horizon LQR by Riccati iteration, run until $P$ stops
changing. [03-lqr-vs-mpc.md](03-lqr-vs-mpc.md#and-it-is-the-same-code) points
out that this loop *is* the backward-in-time value-iteration step of an MPC
with horizon $N$ — LQR is just its fixed point.

**`discrete_model(v, dt)`** is the exact zero-order-hold discretization of the
model above, used because the robot's control period (50 ms) is slow enough
that the continuous-time gains are measurably wrong — see
[01-lqr.md](01-lqr.md#the-version-you-actually-run-discrete-time).

**`lqr_gains_discrete(v, dt, q_e, q_th, r)`** ties the three together: build
$A, B$ at this speed, call `dlqr`, hand back $(k_e, k_\theta)$. This is the
function `run_lqr.py`, `run_mpc.py`, and `mpc_choose_speed` all actually call —
the analytic formula above is a sanity check, not what runs.

## Plant, sensor, and track

**`coerce(e, e_max)`** is the single most important function in the file for
teaching purposes: it clips $e$ to $\pm e_{max}$, which is the one thing a
single light sensor can and cannot tell you. Outside the window the sign is
still right but the magnitude is a lie — see
[01-lqr.md](01-lqr.md#the-three-sensor-states-are-not-the-state).

**`wheel_speeds(v, omega, track_w)`** and **`to_percent(v_wheel, wheel_max)`**
are the differential-drive inverse kinematics and the mm/s → percent
conversion — the same two steps `robot.py`'s `drive()` performs against real
motors.

**`Track`** is a piecewise-constant-curvature path indexed by arclength $s$:
a list of `(length_mm, radius_mm_or_None)` segments, `None` meaning straight.
**`DEMO_TRACK`** — 400 mm straight, a 90° turn of radius 80 mm, 400 mm
straight — is the track behind every worked example in the docs, including
[the head-to-head comparison](03-lqr-vs-mpc.md#the-demonstration).

## The MPC half

**`mpc_choose_speed(e, theta, s, track, candidates, horizon, dt, e_max, ...)`**
is one MPC solve. Full explanation in
[02-mpc.md](02-mpc.md#worked-example-one-mpc-solve-at-the-corner), but in
short: for each candidate constant speed, it re-tunes the LQR steering gains
for that speed, rolls the *previewed* curvature forward for `horizon` steps,
and scores the resulting trajectory — tracking cost plus a heavy penalty for
predicted excursions past $e_{max}$, the soft-constraint trick described in
[02-mpc.md](02-mpc.md#solving-it-properly). The candidate with the lowest
score wins; only its first instant is ever applied before the next period
re-solves everything.

`run_mpc.py` doesn't hand it a real track — with only one sensor there is no
map on board, so it passes a `ConstantCurvature` object holding whatever
curvature the robot is *currently* fighting, as a stand-in for "the road
ahead." That approximation, and how to do better, is the subject of
[02-mpc.md's closing question](02-mpc.md#where-does-the-preview-come-from).

**`run_mpc(track, ...)`** drives `DEMO_TRACK` end-to-end with this solver and
returns a log identical in shape to `run_lqr`'s, so **`summarize(name, log)`**
can report both the same way: peak $|e|$, percent of samples blind, lap time,
mean speed.

## Try it here: move the sliders

The "Try it" list below says to edit constants in `sim.py` and rerun it. On the
web you don't need to: the sliders here are those constants, and the tables and
plots recompute as you move them. Every number comes from the same functions
as the report above.

<div class="pylab" data-lab="sim"></div>

Each item in the list below has a control here:

- **Q_TH** is the $Q_\theta$ slider. Leave it at 0 and the damping ratio stays at
  $1/\sqrt2$ in the gains table. Move it and watch the ratio change.
- **R_W** is the $R$ slider. Drop it from 25 to 5 and the "max v" column of the
  turn-radius table moves, so does the plot, and so does the number of times the
  fixed-speed LQR goes blind.
- **A second turn on `DEMO_TRACK`** is the checkbox. Tick it and the MPC's speed plot
  dips twice.
- **`horizon`** is the horizon slider. Push it down to 3 and the candidate table
  stops rejecting the fast speeds, because the horizon is too short to see the turn
  coming.
